### Análise das três decisões de escopo (pedido explicitamente)

**1. Token `--radius-selector` — proporcional? Sim, mas não obrigatório.** O argumento técnico está certo e é verificável: `rounded-field` é `0.5rem` num quadrado de `size-4` (16px), e 8px de raio em 16px de lado é praticamente um círculo — que lê como radio, não como checkbox. Só que o CLAUDE.md proíbe **cor** bruta, não raio: `rounded-sm` do Tailwind resolveria sem tocar o arquivo de tema que todo derivado herda. O executor escolheu a opção mais cara e **sinalizou ela mesmo como a mais discutível**, o que é o comportamento certo. Veredito: aceitável, com a exigência de documentar no README — um token não documentado é pior que nenhum token.

**2. `Label` do Reka divergindo do kit — aceitável?** Aceitável, **não** ideal. Aceito no PR com um follow-up registrado: ou o Checkbox volta a `<label>` nativo, ou `Input`/`Select` migram para o `Label` do Reka. Dois idiomas para a mesma coisa em um kit de 10 componentes é o começo de uma dívida. O comentário no código explicando o porquê salva metade do problema.

**3. `indeterminate` — escopo além do pedido ou natural?** **Natural.** É o terceiro estado nativo do primitivo (`modelValue: T | 'indeterminate'` está no tipo do Reka, não foi inventado), o `data-[state=indeterminate]` sai de graça, e sem ele o `defineModel<boolean>` estaria mentindo sobre o que o componente aceita. A demo do marca-tudo na vitrine justifica a existência do estado em vez de só expô-lo. Não é gold-plating.

- `expect(control.html()).toContain('lucide:check')` acopla o teste ao nome do ícone no HTML renderizado pelo Nuxt Icon. Funciona hoje; uma mudança de estratégia de render do módulo quebra dois testes por motivo errado.
- `--radius-selector` entra na base sem uso além do Checkbox; se `Radio`/`Switch` nunca chegarem, o `knip` não pega token CSS morto e ele apodrece silenciosamente.

## Vale incorporar à base?

### Alert — **sim, com ajustes**

O componente resolve uma lacuna real: hoje a base só tem canal de mensagem **dinâmico** (`useToast()`), e não há nada para o aviso estático de página (banner de ambiente, erro de formulário já renderizado). É 57 linhas, sem dependência nova, sem token novo, e reaproveita o vocabulário do `Toaster` — o custo de manutenção é próximo de zero.

**Ajustes antes do merge:** (1) linha do `UiAlert` na tabela do README; (2) seletor estável no lugar de `wrapper.find('div')` nos testes; (3) trocar o teste `'não declara live region'` por uma prop opcional `live?: 'polite' | 'assertive'` — proibir a live region por teste vai empurrar o próximo desenvolvedor para um segundo componente, que o `jscpd` reprova. Nenhum é grande.

### Variante `success` — **sim, mas é decisão de produto, não de código**

O **código está impecável** e eu não pediria uma linha de mudança nele: token em par, três camadas, README nos dois lugares, vitrine, teste, verificação no CSS do build, contrastes calculados e corretos.

A pergunta aberta é outra: **a base quer uma paleta semântica ou uma paleta monocromática?** Hoje ela é zinc + `destructive`, e dois componentes (`Toaster`, `Alert`) já contornam a ausência de `success`/`info`. Duas saídas coerentes:

- **Incorporar** — e então incorporar `info` e `warning` no mesmo commit, para não deixar a paleta semântica pela metade. Além disso, **revisar o valor do tema escuro**: 3,30:1 reprova AA para texto normal; `--success: var(--color-green-500)` com `--success-foreground: var(--color-zinc-950)` passa folgado nos dois temas e melhora o precedente em vez de empatá-lo.
- **Não incorporar** — e transformar este diff no exemplo canônico da receita "cor nova = token novo" no README, que é onde ele tem mais valor pedagógico.

Minha recomendação: **incorporar com o valor do dark corrigido**, e abrir um issue para `info`/`warning`. Deixar `Toaster` e `Alert` com comentários de contorno é pior que ter três pares de token.

### Checkbox — **sim, com ajustes**

Checkbox é peça obrigatória de qualquer kit; a ausência dele na base é uma lacuna maior que o `Tooltip` que já entrou. A implementação está correta em a11y, segue a API do `UiInput`, tem `indeterminate` (que é do primitivo, não invenção) e vem com vitrine, teste, `kit-smoke` e README.

**Ajustes antes do merge:** (1) documentar `--radius-selector` na tabela de tokens do README — bloqueante; (2) resolver o `Label` do Reka (voltar a `<label>` nativo, ou follow-up migrando `Input`/`Select`); (3) opcional: alinhar o idioma de foco. **Nada bloqueia o mérito do componente.** Se a preferência for não tocar o `main.css`, trocar `rounded-selector` por `rounded-sm` é uma linha e o resto do diff sobrevive intacto.
