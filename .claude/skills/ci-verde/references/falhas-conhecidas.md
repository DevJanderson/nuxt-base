# Falhas conhecidas de CI — catálogo do projeto

Casos reais primeiro (com o commit da correção quando houver), classes conhecidas depois.
Ao resolver uma falha de ambiente nova, adicione a linha aqui **no mesmo commit**.

| Sintoma | Causa | Correção |
|---|---|---|
| `<binário>: not found` só no CI (`eslint: not found`) — **caso real, commit 3cf647b** | Dependência implícita: o binário está no `node_modules` local (sobra de install antigo ou peer auto-instalado), mas sem entrada no `package.json`; o install limpo do CI não o expõe. Peer **opcional** (`vitest` é opcional no `@nuxt/test-utils`) o pnpm nem chega a instalar | Declarar o pacote em `devDependencies` e commitar o lockfile. Reproduzir exige install limpo — `rm -rf node_modules && pnpm install --frozen-lockfile` —, porque `pnpm verify` reusa o `node_modules` sujo e passa |
| `pnpm smoke` vermelho com `[request error] [fatal]` no log de produção a cada 404 — **caso real, commit a73251b** | `createError({ fatal: true })` no catch-all `app/pages/[...slug].vue`: no SSR o `fatal` faz o Nitro tratar 404 como erro não tratado e logar stack trace (e o h3 ainda emite WARN em dev) | `fatal: import.meta.client` — o `fatal` só é necessário no client, para a navegação interna abrir a página de erro; `statusMessage` curto e ASCII (o h3 sanitiza texto longo), o pt-BR vai em `message` |
| `pnpm smoke` vermelho em `nuxt dev` com `Another Nuxt dev server is already running` | Lock do `nuxt dev` por diretório, disparado quando o dev está com o `pnpm dev` aberto | Já tratado: o script sobe o dev com `NUXT_IGNORE_LOCK=1` em porta sorteada. Se voltar, é sinal de que a variável se perdeu do `stepDev` |
| `pnpm smoke` vermelho no teto do `.output/server` | Dependência pesada nova no bundle do servidor (caso conhecido: `@nuxt/image` com sharp+ipx, 26 MB) | Conferir se a dependência precisa mesmo ir para o servidor; teto novo é decisão consciente — mudar `MAX_SERVER_MB` no topo do `scripts/smoke.mjs` com o porquê no commit |
| `pnpm smoke` verde local e no CI `timeout de 120s aguardando dev ficar pronto` — **caso real, commit f64ce87** | No GitHub Actions o consola força cor ANSI e a linha `Local:` do `nuxt dev` vem com escapes entre `Local:` e `http`; a checagem de prontidão testava o buffer bruto | Filhos do smoke rodam com `NO_COLOR=1`/`FORCE_COLOR=0` e a prontidão casa no texto sem ANSI; reproduzir local com `FORCE_COLOR=1 pnpm smoke` |
| `pnpm smoke` vermelho em produção por `DeprecationWarning`/`ExperimentalWarning` do Node no stderr | Bump de Node (local e CI em versões diferentes): warning de processo sai em stderr, que em produção reprova casando ou não | Corrigir a causa (flag/API depreciada) ou, se for ruído do runtime sem ação nossa, entrada na `LOG_ALLOWLIST` do `scripts/smoke.mjs` com o porquê |
| `pnpm smoke` vermelho no derivado depois de adotar logger (pino + pino-pretty) | O logger imprime `WARN`/`ERROR` legítimos no stdout, e o regex `OFFENSIVE_LINE` os pega | Rodar o smoke com o logger em modo silencioso/JSON (variável de ambiente) ou allowlist específica para o prefixo do logger — nunca afrouxar o regex |
| `ERR_PNPM_OUTDATED_LOCKFILE` no install do CI | `pnpm-lock.yaml` fora de sincronia com o `package.json` (edição manual de deps sem rodar install) | `pnpm install` local e commitar o lockfile junto |
| `Ignored build scripts: <pacote>` e depois binário/hook faltando — **casos reais: esbuild, unrs-resolver, vue-demi, lefthook** | pnpm 11 bloqueia postinstall por padrão | Adicionar o pacote em `allowBuilds` no `pnpm-workspace.yaml` |
| `typecheck` falha no CI e não local (ou vice-versa) | Spec fora de `tests/nuxt/` (fora do include do tsconfig) ou `.nuxt/` desatualizado | Specs sempre em `tests/nuxt/`; rodar `pnpm exec nuxt prepare` |
| Teste com data/hora passa local e falha no CI | Fuso: o CI roda `TZ: UTC`; máquina local provavelmente UTC-3 | Reproduzir com `TZ=UTC pnpm test`; corrigir o teste/código (datas em ISO/UTC), não o fuso do CI |
| `knip` acusa dependência "não usada" que o app usa | Auto-descoberta do Nuxt (coleções `@iconify-json/*`, environments de teste, binários internos) — knip não vê import | `ignoreDependencies` no `knip.jsonc`, com comentário do porquê |
| Você leu "sucesso" mas o run falhou | `gh run watch \| tail` — o pipe substitui o exit code do gh pelo do tail — **caso real** | `gh run watch <id> --exit-status` sem pipe; confirmar com `gh run view` |
| Teste intermitente só no CI | Flakiness: rede real, timers reais, ordem de teste | `registerEndpoint` para HTTP (nunca rede real), fake timers, teste isolado |
| Dev server "validado" era outro processo | Porta 3000 ocupada por instância órfã; Nuxt sobe em outra porta — **caso real na sessão de bootstrap** | Conferir a porta no log do `pnpm dev`; matar pelo PID de quem escuta a porta (`ss -tlnpH`) |
| Config `vite.esbuild.*` sem efeito nenhum (nem erro) — **caso real: strip de console** | Vite 8/rolldown: transform e minify são do oxc; opções `esbuild` são silenciosamente ignoradas | Usar o equivalente rolldown/oxc ou `minify: 'terser'`; **sempre validar por inspeção do bundle** (marcador + grep no `.output/public/`), nunca só pela config aceita |
| Job `gitleaks` vermelho | Segredo (chave, token, senha) commitado — o scan cobre o histórico inteiro, não só o diff | Remover do código, **rotacionar a credencial** (já vazou no histórico) e, em repo público, reescrever o histórico; falso-positivo documentado entra em `.gitleaksignore` |
| Run do `renovate` verde e **nenhum PR** abre; o Dependency Dashboard mostra o grupo em "Awaiting Schedule" — **caso real, commit e9e04b6** | `schedule` no `renovate.json` ("before 8am on monday") somado ao atraso de horas do cron do GitHub: o run caía fora da janela | No self-hosted o horário é o cron do workflow; `renovate.json` **sem** `schedule` (nem no `lockFileMaintenance`) |
| Run do `renovate` com `Workflows update rejection - aborting branch` e o grupo npm inteiro sem PR — **caso real, commit e44a0b6** | Token sem permissão **Workflows**: push em `.github/workflows/` rejeitado, e o bump de action estava no mesmo grupo dos pacotes npm | Permissão Workflows no token **e** `packageRule` `matchManagers: ["github-actions"]` em grupo próprio, para npm nunca ficar refém |
| PR do Renovate só com `package.json` (sem lockfile) e `ERR_PNPM_OUTDATED_LOCKFILE` no CI; no PR, comentário "Artifact update problem" com `ERR_PNPM_NO_MATURE_MATCHING_VERSION` — **caso real, commit a03b25b** | Renovate propôs versão publicada há menos de 24h e o pnpm recusou pela quarentena (`minimumReleaseAge` do `pnpm-workspace.yaml`) | `minimumReleaseAge: "1 day"` + `internalChecksFilter: "strict"` no `renovate.json`, espelhando a quarentena do pnpm |
| Run do `renovate` com `Could not ensure issue` (403 `Resource not accessible by personal access token`) | Token fine-grained sem **Issues: read and write** (o dashboard é uma issue) | Adicionar a permissão; editar o token não muda o valor, o secret continua válido |
| Run do `renovate` com `Repository has changed during renovation - aborting` logo após `Branch created`, sem detalhe em `LOG_LEVEL=info` — **caso real** | Token fine-grained sem **Commit statuses: read and write**: o POST do status `renovate/stability-days` falha e o Renovate traduz em "repo mudou" | Adicionar a permissão. Lista completa do token: Contents, Issues, Pull requests, Workflows, Commit statuses (read-write) + Metadata |
| Run do `renovate` falha em segundos, sem log do Renovate | Secret com nome errado (o workflow lê `secrets.RENOVATE_TOKEN`; o **nome do secret** não é o nome do token) ou token sem o repo em Repository access (`Permission to <repo> denied`) | `gh secret list` para conferir o nome; no token, marcar o repositório em Repository access |
| Run do `renovate` falha em ~10s com `Error: 'token' MUST be passed using its input or the 'RENOVATE_TOKEN' environment variable` — **caso real** | O secret `RENOVATE_TOKEN` não existe no repositório (típico logo depois de copiar o workflow, ou num derivado) | Criar o secret (`gh secret set RENOVATE_TOKEN`); no derivado que não vai usar Renovate, apagar `.github/workflows/renovate.yml` — senão vira run vermelho semanal pelo cron |
| PRs do Renovate marcados "Edited/Blocked" um após o outro, dashboard duplicado (duas issues "Dependency Dashboard") | Dois Renovates no mesmo repo: o app hospedado da Mend instalado na conta **e** o self-hosted | Desinstalar o app da Mend (Settings → Applications) e fechar o dashboard dele; só o self-hosted fica |
| `pnpm lint` morre com `ERR_MODULE_NOT_FOUND … .claude/worktrees/<agente>/.nuxt/eslint.config.mjs` — **caso real, 2026-09-07** | Worktree do Claude Code (agente com `isolation: worktree` ou `EnterWorktree`) é um checkout inteiro dentro do repo; o eslint entra nele, acha outro `eslint.config.mjs` e quebra no `.nuxt/` que não existe lá. `git add -A` ainda leva os diretórios como gitlink | `.claude/worktrees` no `.gitignore`, `{ ignores: [".claude/worktrees/**"] }` no `eslint.config.mjs` e `test.exclude` no `vitest.config.ts` (já na base; o vitest também colhia os `tests/` das cópias); nunca `git add` desses diretórios — `git rm -r --cached .claude/worktrees` se entrarem |
